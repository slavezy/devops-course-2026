## Краткий конспект

DevOps объединяет разработку и эксплуатацию общей ответственностью за результат. Автоматизация сборки, тестирования и выпуска, обратная связь и наблюдение за работающим сервисом помогают доставлять изменения быстрее и надёжнее. Одной установки инструментов для этого недостаточно: нужны сотрудничество и согласованные процессы.

В методичке приведена цепочка развития: Waterfall, Agile-манифест 2001 года, DevOpsDays 2009 года, распространение Docker и затем Kubernetes и инфраструктуры как кода. Для начала работы полезны Git, Linux/Bash, контейнеры и CI/CD; далее - облака и автоматизация инфраструктуры.

## 1. Какую главную проблему решает культура DevOps?

Разрыв между разработчиками, которым нужно быстро выпускать изменения, и эксплуатацией, которой нужна стабильность. Общие цели, автоматические проверки и совместная ответственность уменьшают задержки и ошибки при передаче продукта между командами.

## 2. Что означает CALMS?

- **Culture** - культура сотрудничества и общей ответственности.
- **Automation** - автоматизация повторяемых операций.
- **Lean** - сокращение потерь, ожидания и лишних действий; небольшие партии изменений.
- **Measurement** - измерение результата и принятие решений на основе данных.
- **Sharing** - обмен знаниями, опытом и обратной связью.

Источник: [Atlassian: CALMS](https://www.atlassian.com/devops/frameworks/calms-framework).

## 3. Чем отличаются git add и git commit?

`git add` помещает выбранное содержимое файла в индекс, подготавливая следующий снимок. `git commit` сохраняет этот снимок в локальной истории. Если после `git add` снова изменить файл, для включения новых правок его нужно добавить повторно. Отправка на сервер выполняется отдельно командой `git push`.

Источник: [Pro Git: запись изменений в репозиторий](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository).

## 4. Зачем нужен SSH-ключ?

SSH-ключ позволяет подтвердить право доступа к аккаунту без ввода пароля GitHub при каждой операции. Публичная часть добавляется в GitHub, приватная остаётся на компьютере и используется для криптографического подтверждения владения ключом. Приватный ключ нельзя публиковать; парольная фраза дополнительно защищает его при краже файла. GitHub проверяет подпись, а приватный ключ ему не передаётся.

Источник: [GitHub: подключение по SSH](https://docs.github.com/ru/authentication/connecting-to-github-with-ssh).

## 5. Что означают origin и main в git push origin main?

`origin` - локальное имя удалённого репозитория, обычно созданное при клонировании. `main` - имя отправляемой локальной ветки. При обычной конфигурации команда обновляет одноимённую ветку на сервере. Это разные сущности: адрес сервера и ветка истории.

## 6. Назовите две метрики DORA

В рамках четырёх метрик из методички:

1. **Deployment Frequency** - частота развёртываний в рабочей среде.
2. **Lead Time for Changes** - время от коммита до развёртывания изменения в рабочей среде.

Две другие метрики, указанные в методичке: **Change Failure Rate** (доля неудачных изменений) и **Time to Restore Service** (время восстановления сервиса после инцидента).

## Подготовка к следующему занятию

### Почему в командной разработке не стоит писать всё непосредственно в main?

Непроверенное изменение может нарушить работу общей версии проекта. Отдельная ветка позволяет закончить задачу, проверить изменения и обсудить их в Pull Request перед объединением. Так проще связать изменения с задачей и сохранить основную ветку пригодной к выпуску. Git технически разрешает прямые коммиты; запрет определяется правилами команды. В первой учебной работе прямой push в main предусмотрен заданием.

### Конспект статьи о стандартах GitFlow

В описанном авторами процессе `main` содержит стабильную версию, `develop` объединяет разработку, а `feature`, `release` и `hotfix` служат отдельным видам задач. Команда заранее согласует имена веток, сообщения коммитов, порядок ревью и разрешения конфликтов. Изменения проверяют до слияния; небольшие логичные коммиты облегчают проверку. Для нашей подготовки основной вывод - договориться о правилах совместной работы и проверять изменения перед включением в общую версию.

Материал из задания: [Группа ИТ-компаний Lad: стандарты групповой разработки в GitFlow-команде](https://habr.com/ru/companies/lad_/articles/868212/).
