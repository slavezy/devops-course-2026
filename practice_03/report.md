## Письменные ответы для самопроверки

1. **Merge и rebase.** Merge соединяет ветки и сохраняет отдельный merge-коммит и реальную параллельную историю. Rebase переносит коммиты на новую базу, переписывает их хеши и даёт линейную историю. Rebase уместен для своей ещё не опубликованной feature-ветки; merge — для общей опубликованной истории.
2. **Rebase публичной ветки.** Меняются хеши коммитов, локальные копии коллег расходятся с серверной историей; обычный push отклонится, а force-push может потерять чужие изменения. Поэтому общие опубликованные ветки не перебазируют.
3. **`git rebase -i HEAD~5`.** Открывает последние пять коммитов для редактирования. `pick` оставить, `reword` изменить сообщение, `edit` остановиться для изменения коммита, `squash` объединить с предыдущим и отредактировать общее сообщение, `fixup` объединить и отбросить сообщение, `drop` удалить.
4. **Squash и fixup.** Оба объединяют коммиты; squash позволяет отредактировать общее сообщение, fixup безусловно отбрасывает сообщение присоединяемого коммита.
5. **Cherry-pick.** Применяет изменение выбранного коммита поверх текущей ветки, создавая новый коммит. Полезен, чтобы перенести срочный фикс без слияния всей ветки.
6. **Восстановление потерянного коммита.** Найти хеш через `git reflog`, затем создать ветку или перейти к коммиту, например `git branch recovered <hash>`.
7. **Revert и reset.** `reset` перемещает указатель ветки и может убрать коммиты из локальной истории; `revert` создаёт новый коммит, отменяющий изменение. В общей публичной ветке revert сохраняет историю и безопаснее.
8. **Multi-remote.** Второй сервер добавляется `git remote add mirror <URL>`. Несколько push URL у `origin` настраиваются `git remote set-url --add --push origin <URL>`; затем `git push origin <ветка>` отправляет в оба назначения.
9. **Git hooks.** Это локальные скрипты, запускаемые Git до или после события. Например, `pre-commit` может запускать тесты или форматтер; этот проект проверяет формат сообщения хуком `commit-msg`.
10. **Forking Workflow.** Разработчик форкает оригинал, работает в своей копии, регулярно получает изменения из upstream и предлагает изменения через PR/MR. В GitHub Flow обычно работа идёт с feature-ветками в одном общем репозитории и интегрируется через PR.
